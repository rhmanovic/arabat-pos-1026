# Database

Status: **Conventions defined. No schema or migrations exist yet.**

## 1. Engine and access
- PostgreSQL (current supported major; local dev cluster is PostgreSQL 16+).
- Access through Drizzle ORM; schema changes only through versioned SQL
  migrations committed to the repository (drizzle-kit). No manual schema edits.
- Two database roles:
  - `app_owner` — owns schema, runs migrations.
  - `app_runtime` — used by the API; no superuser, no `BYPASSRLS`.

## 2. Naming conventions
- `snake_case` for tables and columns; tables are plural (`products`, `sales`).
- Primary key: `id uuid` (UUIDv7 generated by the application, time-ordered).
- Foreign keys: `<entity>_id`.
- Timestamps: `timestamptz`, stored in UTC: `created_at`, `updated_at`.
- Soft state via explicit status columns (`status`), not hidden flags, for
  master data. Financial/ledger rows are never deleted.

## 3. Multi-tenancy rules
- Every tenant-owned table has `tenant_id uuid not null` referencing `tenants(id)`.
- Every tenant-owned table has RLS **enabled and forced**, with a policy:
  `tenant_id = current_setting('app.tenant_id')::uuid`.
- Unique constraints are scoped per tenant, e.g. `unique (tenant_id, sku)`.
- Child tables reference parents with composite keys `(tenant_id, parent_id)` to
  make cross-tenant references impossible.
- Platform tables (`platform_operators`, plans, etc.) are not tenant-scoped and
  are accessible only through the platform module.

## 4. Money and quantities
- Money is stored as **`bigint` in minor units** with an accompanying
  `currency char(3)` (ISO 4217). KWD minor unit = fils, 1 KWD = 1000 fils.
  Example: 1.250 KWD → `1250`.
- Never use `real`, `double precision`, or `money` types.
- Currency exponent comes from a currency table/constant (KWD=3, USD=2, ...),
  never assumed as 2.
- Quantities: `numeric(18,3)` (supports weighed items); handled in TypeScript
  with a decimal library, never JS `number` arithmetic for financial results.
- Rates (tax, discount %) stored as `numeric` basis points or exact decimals,
  documented per column.

## 5. Append-only financial records
- Sales, sale lines, payments, refunds, stock movements and audit entries are
  insert-only. Corrections are compensating records.
- Inventory on-hand is derived from the stock-movement ledger (a cached balance
  table may exist but must be updated in the same transaction as the movement).

## 7. Migration workflow
1. Change the Drizzle schema in the owning module.
2. Generate a SQL migration; review the SQL by hand (RLS, constraints, indexes).
3. Apply locally; run the DB test suite including tenant-isolation tests.
4. Commit schema + migration together. Never edit an applied migration.
